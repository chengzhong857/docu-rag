# docu-rag · 中文文档问答系统

一个从零实现的中文 RAG（检索增强生成）问答系统。支持 PDF / DOCX / TXT / Markdown 入库，
回答带原文页码引用；核心工作在检索侧——向量 + BM25 混合召回、可选交叉编码器重排、
以及一套可复现的检索质量评估。

纯 CPU 可跑，无需 GPU，模型全部本地推理。

## 效果

评估集 30 条可回答问题（覆盖事实型、对比型、推理型），3 条应拒答问题。
判定口径：前 k 条检索结果中包含 gold 关键词即算命中。

| 检索方案 | Recall@1 | Recall@3 | Recall@5 | MRR |
| --- | --- | --- | --- | --- |
| 仅向量（bge-small-zh） | 0.900 | 1.000 | 1.000 | 0.944 |
| 仅 BM25（jieba） | 0.867 | 0.967 | 0.967 | 0.917 |
| 混合 / 归一化加权 α=0.80 | **0.967** | 0.967 | **1.000** | **0.975** |
| 混合 / RRF α=0.80 | 0.933 | 0.967 | 1.000 | 0.957 |

混合检索相比纯向量把 Recall@1 从 0.900 提到 0.967，MRR 从 0.944 提到 0.975。

> 注意样本量：30 条问题下，1 条差距约等于 3.3 个百分点，因此两张方案之间的
> 几个点差异只能作为方向参考，不足以声称统计显著。要下更硬的结论需要把
> 评估集扩到 200 条以上，并用自助法估计置信区间。

工程指标：44 个文本块的索引构建耗时 2.1 秒；单次检索（含查询向量化）约 100~200 ms（CPU）。

## 快速开始

```bash
# 1. 安装依赖
pip install -r requirements.txt

# 2. 下载向量模型（国内建议走 ModelScope）
python -m scripts.download_model

# 3. 把文档放进 data/docs/，然后建库
python -m scripts.ingest --reset

# 4. 配置大模型（可选，不配则降级为纯检索模式）
cp .env.example .env   # 填入 LLM_API_KEY

# 5. 启动界面
streamlit run app.py
```

命令行查询与评估：

```bash
python -m scripts.query "中文文档做 RAG 时每块切多少字比较合适？" --top 5
python -m scripts.evaluate --sweep     # 输出四种方案对比 + alpha 扫描
```

## 设计取舍

### 1. 为什么自己做中文切分，不用 LangChain 的 RecursiveCharacterTextSplitter

它的分隔符优先级是按英文习惯设计的（`\n\n` → `\n` → 空格），对中文的
`。！？；` 覆盖不足，容易把一句完整的话切成两半，embedding 语义被打散。

本项目的策略是两层：先按 Markdown 标题做结构切分，标题作为新块的起点
（这样块本身带上章节语境，指代类问题召回明显更好）；再在块内按中文标点切句，
累积到 420 字落块，相邻块保留 80 字重叠。超长无标点段落用滑动窗口兜底。

### 2. 为什么向量和 BM25 都要，而不是只留一个

两者失效场景恰好互补。

纯向量对「语义相近、字面不同」的查询强，但对精确匹配弱：问「bge-small-zh 的向量维度是多少」，
`512` 这个数字在向量空间里几乎不携带语义方向。纯 BM25 反过来，问「怎么防止模型背题」
它抓不到「过拟合」这个词。

实测数据也印证了这一点：BM25 单独用 Recall@1 只有 0.867，向量单独用 0.900，
混合之后 0.967。

### 3. 融合方式选了加权归一化，同时保留 RRF 做对照

min-max 归一化加权的优点是能保留分数大小的信息，但两路分数量纲不同，
需要归一化；RRF 只用排名、对量纲不敏感，更鲁棒但丢掉了「差距有多大」的信息。
两者都实现了，评估脚本里可以直接对比，实测本项目上加权略优（MRR 0.975 vs 0.957）。

### 4. α=0.80 是量出来的，不是拍的

初始按经验设了 0.65，跑 `--sweep` 扫描 0.0 到 1.0 之后发现 0.80 明显更好
（MRR 0.942 → 0.975）。默认值因此改成了 0.80，代码注释里留了扫描结论。

### 5. 为什么块大小是 420 字

中文一个汉字的信息量约等于英文 1.5~2 个 token，420 字约对应 600~800 token，
在「检索粒度」和「上下文完整性」之间取平衡。另外 BGE 的最大输入是 512 token，
块再长会被静默截断，尾部内容实际上没进向量，这是很难察觉的召回缺失。

### 6. 没有 API Key 也能跑

大模型只负责最后的归纳，检索质量才是 RAG 的核心。所以没配 Key 时系统降级为
检索模式，直接展示最相关的原文片段。这样项目本身可离线运行、可评估、可演示。

## 踩过的坑

**BM25Plus 在小语料下会退化。** 一开始用 `rank_bm25` 的 `BM25Plus`，理由是不会出现
负 IDF。实测发现它的评分含一个与词频无关的 delta 项，导致任何文档只要查询词
在全局有 IDF 就能拿到基础分——44 个块全部得分非零，最低分恰好等于查询词 IDF 之和。
查询词命中很少时，大量零重叠的块会挤进 top-k，排序完全失效。
换回 `BM25Okapi`（零重叠文档精确得 0 分）后恢复正常。

**jieba 会把英文标识符切碎。** `BatchNorm` 被切成 `batch` + `norm`，
`bge-small-zh-v1.5` 被切成若干碎片，关键词信号直接消失。解决方法是先用正则把
拉丁字母开头的串整体抽出并小写化，剩余中文再交给 jieba。

**停用词表不能删否定词。** 把「不」加进停用词会让「不支持删除」变成「支持删除」，
语义直接反转。否定词必须保留。

## 已知问题

- **缩写与全称不匹配。** 评估集中「BatchNorm 和 LayerNorm 的核心差别是什么」在所有
  含 BM25 的方案里都未命中：语料里写的是「批归一化（Batch Normalization）」「层归一化
  （Layer Normalization）」，查询用的却是缩写 `BatchNorm`，两者在词表和向量空间里都
  没有交集。可行的解法是构建领域同义词表做查询扩展，或引入更强的重排模型，
  本项目暂未实现。
- **评估集偏小。** 30 条问题不足以下统计显著的结论，见上文说明。
- **DOCX 没有物理页。** 按 1500 字切「逻辑页」做引用定位，比真实页码粗。
- **重排默认关闭。** `bge-reranker-base` 约 1.1GB，CPU 上单次查询增加 1~2 秒延迟，
  需要显式设置 `USE_RERANK=1` 开启。

## 项目结构

```
docu-rag/
├── app.py                    Streamlit 界面
├── src/
│   ├── config.py             全部可调参数与模型路径解析
│   ├── loader.py             多格式解析，保留页码
│   ├── splitter.py           中文感知切分
│   ├── embedder.py           向量化（本地 BGE）
│   ├── index.py              FAISS + BM25 混合检索、重排
│   ├── generator.py          提示词构造与大模型调用
│   └── pipeline.py           端到端流水线
├── scripts/
│   ├── download_model.py     从 ModelScope 拉模型
│   ├── ingest.py             建库
│   ├── query.py              命令行查询与 badcase 排查
│   └── evaluate.py           检索质量评估
├── data/docs/                知识库文档（示例为 6 篇 AI 主题笔记）
└── eval/qa_set.jsonl         评估集
```
